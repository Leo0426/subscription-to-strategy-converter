# 订阅刷新、稳定性与设备排查

本次 P0–P2 调整覆盖 Profile 更新一致性、重复刷新的开销、网络故障边界和诊断证据。它改善 Subflow 生成与刷新配置的行为；节点带宽、服务端地区限制和手机实际登录结果仍由使用环境决定。

## P0：编辑后不再被旧请求覆盖

每次保存 Profile 都增加 `generation`，清除所有客户端的旧产物。请求完成时，必须在同一数据库事务内核对 generation 才能写入配置；如果期间发生编辑，就按当前偏好重新生成。连续编辑超过三次尝试会返回 409，避免无限重试。

这修复了「旧请求仍在下载 → 保存新出口 → 旧请求完成并把旧出口写回缓存」的问题。generation 只用于并发一致性，不建立历史版本或回滚系统，继续遵循 ADR 0012。

## P1：缓存与网络边界

同一 Profile、generation、客户端目标和配置标识的成功产物，默认可复用 30 秒。配置标识包含 Leo、服务目录、应用 Python 源码摘要及影响输出的环境设置摘要。源码升级需重启应用。上游节点变化在缓存过期后的下一次请求重新获取；没有另一层长期节点缓存。

- 每次读取仍检查 token；浏览器和代理响应保持 `Cache-Control: no-store`。
- `force_refresh=true` 跳过新鲜产物缓存，但同一时刻的相同刷新仍会合并。工作台的「强制刷新已保存的订阅」刷新数据库里的已保存偏好，不会提交未保存的草稿。
- 同一进程中，相同编译请求合并；不同客户端同时读取相同来源时，也可共享正在进行的上游读取。共享结果复制后再交给各编译器，避免相互修改。
- 每个协调器最多保留 64 个不同的进行中任务。取消一个请求不影响其他等待者；全部取消后清理上游任务。跨进程不合并任务，数据库 generation 核对仍生效。
- 外部订阅或适配器不可用时，仅可回退到同一已保存 generation、同一客户端的最后成功产物。基础策略或编译器已更新但上游故障时，也允许使用旧标识产物，明确标记 stale，并保留原生成时间。解析错误、无效节点、内部编译错误和鉴权失败不能借此回退。
- 新鲜命中保留编译警告；发现来源内容无效时移除受影响客户端的旧产物，避免下一次命中将该失败掩盖。

网络连接池随应用生命周期创建和关闭。连接可复用，但 Cookie 只属于一次来源请求及其重定向链；同域的其他订阅、DoH 请求和兼容适配器不会获得这份 Cookie。Cookie 的域名、路径和 Secure 限制继续生效。

网络总时限默认 20 秒，涵盖来源解析、下载、重定向、重试及可选兼容转换的异步等待。HTTP 502/503/504 和传输错误在每一跳最多重试一次，仍受总时限约束；403 不自动重试。每次重定向都重新验证目的地址，最多请求六跳。响应按解码后的字节流限制大小；fake-IP 的 UDP DNS 与 DoH 回退并行，并清理未完成的异步任务。该网络时限不用于保证同步编译或数据库操作的硬实时上限。

| 环境变量 | 默认值 | 有效范围 |
| --- | --- | --- |
| `SUBFLOW_CACHE_TTL` | 30 秒 | 0–300 秒；0 关闭新鲜产物复用 |
| `SUBFLOW_FETCH_TIMEOUT` | 20 秒 | 0.05–60 秒 |
| `SUBFLOW_MAX_SUBSCRIPTION_BYTES` | 5242880 字节（5 MiB） | 1024–20971520 字节 |

数值越界会钳制到范围内；无法解析或非有限数值使用默认值。普通部署建议保留默认值，按故障证据调整。

## P2：看清设备拿到什么、请求走到哪里

Profile 订阅的首行注释包含 `generation`、`revision` 和 `generated-at`。这些字段不包含来源链接或 token。它们标识已保存偏好、基础配置与生成时间；节点内容还可能随上游变化，需结合生成时间核对。产物元数据同时保存正文摘要，正文摘要不包含首行身份注释。

Shadowrocket 原生节点订阅保持机场正文不变，不插入首行注释，以免破坏 Base64 或其他原生格式；通过同名 `X-Subflow-*` 响应头查看生成标识。不同来源格式分别请求和合并进行中任务，修改 `SUBFLOW_SHADOWROCKET_USER_AGENT` 会使已有发布缓存失效。

响应头提供 `X-Subflow-Cache`（`fresh`、`hit`、`stale`）、`X-Subflow-Generation`、`X-Subflow-Revision`、`X-Subflow-Generated-At` 和 `X-Subflow-Age`。回退额外带 `X-Subflow-Stale: true`。旧数据库中没有元数据的历史产物，需要成功刷新一次才能补齐身份字段。

工作台显示各客户端的配置标识、生成时间和上次回退状态。服务器生成成功不代表设备已经下载并启用；客户端仍需更新订阅。

实测诊断默认在工作台采样三轮，总时限 30 秒；API 的 `samples` 可设为 1–3。结果包含实际观察节点、失败比例、成功请求耗时中位数和最大最小差值，并检查采样前后出口是否变化。三轮只是短时观察，耗时差值不等同于长期网络抖动。诊断不会修改客户端当前选择。

Surge 额外解释登录、API、移动端和资源域名的当前规则与最终出口，最多八个域名、三个并发命令，隐藏规则提供方 URL。Mihomo 的观察范围仍是控制器策略组及节点探测，不等同于实际应用请求命中记录。两者均不能证明完整登录或对话成功。

电脑 Surge 正常、iPhone App 不正常时，按以下顺序核对：

1. 在工作台强制刷新已保存订阅，然后分别让 Mac 和 iPhone 更新并启用它；对照首行标识与生成时间，排除旧配置或 stale 产物。
2. 对照两端 ChatGPT / Claude 策略组实际选择的节点。相同订阅链接不保证两端保存的策略选择相同。
3. 在手机请求记录中检查 `ios.chat.openai.com`、`auth.openai.com`、`chatgpt.com`、`ws.chatgpt.com`、`cdn.openaimerge.com`、`humb.apple.com`，以及 `claude.ai`、`api.anthropic.com`、`platform.claude.com`、`bridge.claudeusercontent.com` 的实际出口和失败状态。记录错误和域名即可，不包含 token、订阅链接或对话内容。
4. 比较客户端版本、Wi-Fi / 蜂窝网络结果。工作台连接的是所配置的 Mihomo 或本机 Surge，无法直接读取手机状态。

现有 AI 固定/手动出口、600 秒惰性健康检查和 Leo 规则数量预算保持原有设计。诊断结果不会触发自动换节点，也没有新增后台持续探测。

## 升级与验证

首次访问数据库会自动补充 `generation` 和 `artifact_metadata` 列；老 Profile 的 ID、token 和订阅链接保留。升级部署前保留数据库备份；回退使用对应版本及备份，避免旧程序写入后破坏新缓存元数据的一致性。

本地验证（2026-09-21）：518 项自动化测试通过，包含编辑/刷新竞态、缓存失效、取消与限额、老数据库迁移、重定向 Cookie 隔离和异常 DNS 响应；服务目录同步、JavaScript 语法与浏览器保存/强制刷新流程通过。带身份注释的合成配置通过 Surge CLI 和 Mihomo v1.19.31 原生校验。

144 节点合成订阅、20 ms 模拟上游等待、临时 SQLite 的进程内 API 测量：五个并发刷新由原来的五次上游读取降为一次；12 次暖缓存请求均不读取上游。Surge 暖请求中位数 0.72 ms，Mihomo 0.80 ms；强制刷新分别为 70.80 ms 和 105.06 ms。小样本 p95 分别为暖缓存 1.07 / 1.11 ms、强制刷新 80.93 / 112.25 ms。这些数字用于验证服务器重复工作减少，不代表真实网络速度或客户端启动时间。

本轮未部署到运行环境，也没有完成手机 ChatGPT / Claude 登录验收。可重复的行为测试位于 `tests/test_publication_refresh.py`、`tests/test_network_bounds.py` 和 `tests/test_workbench_v5.py`；本地测量脚本与记录位于 `.scratch/stability-speed-review/`。
