# Subflow 6.1

镜像：`subflow:6.1-amd64`，平台：`linux/amd64`，应用版本：`6.1.0`。

## 发布内容

三个客户端统一采用“机场负责连接配置，Subflow 负责分流”：原生配置作为底稿，只调整分流规则及必要策略组，避免模板覆盖机场的 DNS、节点参数和其他公共设置。

- **Surge**：保留 `[General]`、`[Host]`、原始 `[Proxy]`、其他非分流段和代理链依赖。生成策略组重名时改名并同步规则引用；节点选择映射回机场原名。移除上游 `#!MANAGED-CONFIG`，使后续更新继续通过 Subflow。
- **Mihomo**：保留原生 YAML 公共设置、节点字段与名称、原有策略组和 Provider。原生节点不再经过跨格式修正；机场未设置的 DNS、TUN 等选项保持缺省。机场使用全局或直连模式时切换为规则模式，并显示提示。
- **Shadowrocket**：以 Shadowrocket 身份获取上游，节点订阅原文传递，保留 Base64、未知参数及备注等内容。机场提供完整 INI 时，配套配置保留非分流段；机场只提供节点时，配套配置仅生成策略组和规则，不添加公共连接设置。
- 同一订阅地址按目标客户端分别读取并缓存。Shadowrocket 原文不插入 Subflow 注释；产物身份保留在响应头中。
- 阻止工作区中间格式丢失原生连接字段后继续发布；需要完整来源时，明确要求通过 `/render` 或订阅接口生成。

本版本也包含 [6.0](6.0.md) 的并发刷新保护、产物缓存、网络总时限与大小限制、运行时诊断、AI 会话规则和 AnyTLS 支持。原生配置边界见 [ADR-0016](../adr/0016-source-owned-connectivity.md)。

## 升级与回退

升级前停止旧容器，备份数据库目录及存在的 WAL/SHM 文件。沿用原数据挂载、端口、环境变量和访问地址，保留 Profile ID、token 与订阅链接。6.1 沿用 6.0 数据结构；从 5.1 或更早版本升级时，会补充 generation 和产物元数据列。

```sh
sha256sum -c subflow-6.1-linux-amd64.tar.gz.sha256
docker load -i subflow-6.1-linux-amd64.tar.gz
docker run -d --name subflow-6-1 \
  --restart unless-stopped --platform linux/amd64 \
  -p 8000:8000 -v subflow-data:/app/data \
  subflow:6.1-amd64
```

macOS 可使用 `shasum -a 256 -c subflow-6.1-linux-amd64.tar.gz.sha256` 校验归档。上面的挂载适用于新部署；已有部署必须使用原数据目录或卷。

需要回退时，停止 6.1 容器，恢复升级前数据库备份，再用原镜像和原部署参数启动。特别是回退到 5.1 或更早版本时，不要让旧版本持续写入已迁移的数据库。

## 部署后验证

1. 确认容器进入 healthy，`/health` 成功、`/openapi.json` 显示 `6.1.0`、页面显示 `6.1`。
2. 打开原 Profile，强制刷新所选客户端的订阅，确认保存的服务出口仍有效。
3. 在 Surge 与 Mihomo 中对照机场原配置，确认节点参数、DNS 和其他公共设置保留，分流规则更新。
4. Shadowrocket 同步刷新节点订阅和配套配置，并启用配套配置；节点订阅原文的生成标识通过响应头查看。
5. 在实际设备上选择相同节点验证连通性和服务访问，尤其是原先 Surge iOS 全线报红的问题。

## 构建与验收记录

本次交付为本地 amd64 镜像及压缩归档。打包前提交代码，构建后在 `dist/docker/subflow-6.1-build.json` 记录提交 SHA、镜像 ID、归档 SHA-256，以及自动化测试、容器健康检查、三种客户端的原生配置保留、镜像源文件一致性和归档重新加载结果。

镜像只复制应用、公开模板和生产依赖。实际设备连通性及手机端登录结果需在部署后验证，不能由配置生成测试替代。
