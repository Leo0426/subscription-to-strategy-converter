# Subflow 6.0

镜像：`subflow:6.0-amd64`，平台：`linux/amd64`，应用版本：`6.0.0`。

## 发布内容

- 修复 Profile 刷新与编辑并发时，旧请求可能覆盖新策略产物的问题。每次保存递增 generation，并以原子条件写入各客户端产物。
- 增加 30 秒可配置的新鲜产物缓存、相同请求合并和跨目标上游读取合并；工作台支持强制刷新已保存的订阅。
- 复用应用级 HTTP 连接池，并限制总刷新时间、响应大小、重定向和瞬时错误重试。一次订阅的重定向 Cookie 保留在该请求内，不与其他订阅共享。
- 为产物增加 generation、配置 revision、生成时间和缓存状态；多轮运行时诊断展示失败率、耗时波动、出口稳定性及 Surge 移动端相关域名路径。
- 扩充 ChatGPT / Claude 会话域名规则，保持 AI 出口固定或手动选择，不根据普通测速自动切换。
- 支持 AnyTLS 的 Mihomo / Surge 来源，以及 Mihomo、Surge、Shadowrocket 输出；目标客户端的版本限制会作为兼容提示显示。

完整缓存和设备排查边界见 [订阅刷新、稳定性与设备排查](../subscription-refresh.md)，AnyTLS 字段映射见 [AnyTLS 兼容说明](../anytls-compatibility.md)。

## 升级与回退

升级前停止旧容器并备份数据库目录，包含存在的 WAL/SHM 文件。6.0 首次访问数据库时会自动增加 Profile generation 和产物元数据列，保留 Profile ID、token 及订阅链接。

```sh
sha256sum -c subflow-6.0-linux-amd64.tar.gz.sha256
docker load -i subflow-6.0-linux-amd64.tar.gz
docker run -d --name subflow-6 \
  --restart unless-stopped --platform linux/amd64 \
  -p 8000:8000 -v subflow-data:/app/data \
  subflow:6.0-amd64
```

macOS 校验归档可使用 `shasum -a 256 -c subflow-6.0-linux-amd64.tar.gz.sha256`。已有部署应沿用原端口、环境变量、数据挂载和重启策略，不要用空目录覆盖原数据库。

需要回退时，停止 6.0 容器，恢复升级前的数据库备份并使用原 5.1 镜像和部署参数。不要让旧版本持续写入已经由 6.0 迁移的数据库。

## 部署后验证

1. 等待容器进入 healthy，确认 `/health` 返回成功、`/openapi.json` 显示 `6.0.0`，页面显示 `6.0`。
2. 打开原 Profile，强制刷新已保存的 Mihomo / Surge / Shadowrocket 输出，确认 generation、revision 和生成时间更新。
3. 让每个实际客户端刷新订阅；核对配置首行身份、AI 策略的实际节点和失败请求的规则路径。
4. 分别验证 ChatGPT / Claude 登录、API 与内容域名。服务器生成或通用探测成功不代表手机 App 登录成功。
5. 观察容器日志、刷新耗时和 stale 响应。出现持续 `X-Subflow-Stale: true` 时先排查上游订阅或兼容适配器。
