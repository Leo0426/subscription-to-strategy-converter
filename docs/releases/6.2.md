# Subflow 6.2

镜像：`subflow:6.2-amd64`，平台：`linux/amd64`，应用版本：`6.2.0`。

## 发布内容

Mihomo 替换机场业务规则后，会清理不再被使用的机场策略组、规则 Provider、代理 Provider 和子规则，减少重复展示及无用下载。

- 从原生节点、DNS、TUN、监听配置和生成策略追踪完整依赖链，保留仍在使用的机场定义。
- 在解决名称和缓存路径冲突前清理旧定义，避免无用的重命名和假冲突。
- 保留节点代理链、DNS 规则集和出口、特殊 DNS、动态 Provider、Rematch 子规则等引用；支持机场原生字段别名和数值形式。
- 对仍在使用的外部节点集合或表达式动态改写的节点，保留可能依赖的机场组和子规则，并显示提示。没有引用的外部集合仍会清理。
- 节点原始字段、DNS、Hosts、端口和其他公共设置继续保留；三个客户端的原生配置保留策略沿用 6.1。

规则维护边界见 [原生连接配置决策](../adr/0016-source-owned-connectivity.md)。

## 升级与回退

6.2 沿用 6.1 的数据库结构。升级前停止旧容器并备份原数据目录及存在的 WAL/SHM 文件，沿用原端口、环境变量、数据挂载和访问地址，保留 Profile ID、token 和订阅链接。

```sh
sha256sum -c subflow-6.2-linux-amd64.tar.gz.sha256
docker load -i subflow-6.2-linux-amd64.tar.gz
```

macOS 可使用 `shasum -a 256 -c subflow-6.2-linux-amd64.tar.gz.sha256`。

新部署示例：

```sh
docker run -d --name subflow-6-2 \
  --restart unless-stopped --platform linux/amd64 \
  -p 8000:8000 -v subflow-data:/app/data \
  subflow:6.2-amd64
```

已有部署必须使用原数据目录或卷。回退时停止 6.2 容器，恢复升级前数据库备份并使用原镜像和部署参数启动。

## 部署后验证

1. 确认容器 healthy，`/health` 成功、`/openapi.json` 显示 `6.2.0`、页面显示 `6.2`。
2. 在原 Profile 中强制刷新 Mihomo 订阅，再让客户端刷新；核对原有服务出口仍有效。
3. 确认无引用的机场组已清理，原生节点和公共设置保持一致；仍有动态依赖时检查对应提示。
4. 在实际设备验证节点连接和服务访问。Surge 与 Shadowrocket 继续使用各自的原生订阅流程。

## 构建与验收记录

先提交代码，再构建本地 amd64 镜像和压缩归档。提交 SHA、镜像 ID、归档 SHA-256、测试数量、容器健康状态、原生配置保留与清理检查、镜像文件一致性及归档重新加载结果记录在随包提供的 `subflow-6.2-build.json`。

上一轮修复验收的机场样本清理了 53 个旧策略组，输出保留 14 个策略组，144 个原生节点及公共设置保持一致。这个数量仅代表该样本；实际清理数量取决于机场配置的依赖关系。

镜像只复制应用、公开模板和生产依赖。配置与接口验收不代替实际设备连通性验证。
