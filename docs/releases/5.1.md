# Subflow 5.1

镜像：`subflow:5.1-amd64`，平台：`linux/amd64`，应用版本：`5.1.0`。

## 修复内容

修复部分 Shadowsocks HTTP obfs 节点在 Surge 可用、OpenClash 测速全部失败的问题。
输入的混淆 Host 如 `cdn.example.com:` 带空端口冒号，Mihomo 再追加节点端口会
生成错误的 Host。5.1 在生成 Mihomo 配置时去掉这个尾部冒号，同时保留共享节点数据、
其他插件、TLS obfs、显式端口和 IPv6 字面量。Clash 与 Surge 两种订阅输入都覆盖此修正。

5.0 的工作台、Profile ID、token、订阅地址和数据库格式保持兼容，无数据库迁移。
节点测速、服务解锁探测与真实登录/视频播放是不同的验证结果。

## 导入与升级

```sh
sha256sum -c subflow-5.1-linux-amd64.tar.gz.sha256
docker load -i subflow-5.1-linux-amd64.tar.gz
```

macOS 使用 `shasum -a 256 -c`。已有部署替换镜像为 `subflow:5.1-amd64`，
保持现有端口、环境变量、数据库挂载和容器重启策略。停止旧容器后先备份原数据库目录，
包含存在的 WAL/SHM 文件；保留旧镜像供回退。不要用空目录覆盖原数据挂载。

启动后检查 `/health`、`/openapi.json` 的版本 `5.1.0`，在 OpenClash 更新原订阅后测速。
如果上游暂时不可用，Profile 仍可能返回标有 `X-Subflow-Stale: true` 的旧缓存配置；
恢复上游后再刷新。已安装在路由器上的 HTTP obfs 覆写修正可继续保留，它是幂等的。

全新安装示例：

```sh
docker run -d --name subflow --restart unless-stopped \
  --platform linux/amd64 -p 8000:8000 \
  -v subflow-data:/app/data subflow:5.1-amd64
```

如需回退到 5.0，停止新容器，使用旧镜像和原部署参数；必要时恢复升级前数据库备份。
5.0 会重新产生此次修复的错误 Host，应保留路由器侧覆写修正。

## 验收范围

本次交付为本地 amd64 镜像与归档，不自动替换 NAS 上的生产容器。
归档旁的 `subflow-5.1-build.json` 记录镜像 ID、SHA-256、测试和容器验收结果。

打包验收：446 项测试通过，服务目录同步通过；amd64 容器 health=healthy，HTTP 健康检查、
5.1 页面/API 版本及两种合成订阅输入的四种客户端输出检查通过。镜像内 59 个应用与模板
文件逐一校验和工作区一致，归档的标签、amd64 架构及完整性校验通过。

打包前已在实际路由器验证等价修正：128 个节点完成 Host 修正，98 个节点通过该次测速；
Netflix、Disney+、HBO Max 内置探测返回香港支持，YouTube 请求返回 200。
上述是真实配置修正的验证，不代表新镜像已部署到 NAS，也不代表账号登录和视频播放已验证。

镜像只复制应用、公开模板和生产依赖，不包含个人订阅、节点凭据、生产数据库或排障备份。
