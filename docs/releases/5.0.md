# Subflow 5.0

镜像：`subflow:5.0-amd64`，平台：`linux/amd64`，应用版本：`5.0.0`。

## 使用变化

1. 选择使用的客户端，再读取原始订阅。
2. ChatGPT 等服务可固定一个节点；客户端自选与主备故障切换是独立选项。主备探测使用通用连通性地址，不代表服务解锁。
3. 检查界面显示结构错误、各客户端的协议/规则/DNS兼容提示。修正阻断项后保存，修改任一设置需要重新检查。
4. 打开已有 Subflow 链接即可更新原 Profile，ID、token 和链接保持不变。不要点击“新建订阅”来修改原订阅。
5. 旧快照有明确升级入口，先看新增/移除规则、被替换的策略组和无法保留的出口，应用到草稿后检查并保存。升级前不改变原配置。

ChatGPT 规则现在涵盖主站、登录与资源域名。保留 Mihomo fake-ip 与节点专用 DNS；Surge 无法等价保留节点专用 DNS 的情况在发布检查中明确告警。不能仅凭 fake-ip 开关判断故障原因，应使用同一节点比较原配置和转换配置的实际访问。

## 安装镜像

在镜像归档所在目录运行：

```sh
sha256sum -c subflow-5.0-linux-amd64.tar.gz.sha256
docker load -i subflow-5.0-linux-amd64.tar.gz
docker run -d --name subflow --restart unless-stopped \
  --platform linux/amd64 -p 8000:8000 \
  -v subflow-data:/app/data \
  subflow:5.0-amd64
```

macOS 可使用 `shasum -a 256 -c` 校验。浏览器访问服务器的 8000 端口。供路由器/手机使用时，从它们可达的服务器地址打开工作台，或设置 `SUBFLOW_PUBLIC_BASE_URL` 为现有公开访问地址；保持原地址可让现有订阅链接继续使用。

镜像不含个人订阅、节点凭据、生产数据库或本地测试数据。

## 已有部署升级与回退

本次没有数据库表结构迁移。停止旧容器后备份原数据库目录（包含可能存在的 WAL/SHM 文件）或原 volume；记录旧镜像标签及原端口、volume、环境变量。用新镜像替换容器，复用原数据挂载和访问地址。不要覆盖原数据目录或创建一个空 volume 代替它。

回退需要旧镜像和升级前数据库备份：停止新容器，恢复该备份后用原参数启动旧镜像。5.0 新建/升级的服务偏好不保证旧版本能够理解；只换回旧镜像不足以回退这些 Profile。保留备份直到客户端刷新和实际访问验收完成。

## 可选客户端实测

默认只做静态检查，Docker 内没有 Surge Mac。运行态连接由管理员通过服务器环境变量配置，前端不提交控制端点或密钥。

- Mihomo/OpenClash：`SUBFLOW_MIHOMO_CONTROLLER=http://客户端可达地址:9090`，以及客户端已配置的 `SUBFLOW_MIHOMO_SECRET`。地址必须能从容器访问；容器的 localhost 指向容器自身。
- 本机 macOS 运行：自动发现已安装的 Surge CLI；也可设置 `SUBFLOW_SURGE_CLI`。需要支持 `rule explain` 与 `http probe` 的 Surge 版本且客户端已启动。

勾选客户端实测后才发起探测。Mihomo 读取预期策略组的当前选择并探测该节点，不能证明浏览器请求命中了该组；Surge 读取当前规则选择。未配置专用探测的服务只显示通用连通性结果。探测不会切换客户端节点，也不验证完整登录/对话。Mihomo 接口契约参考[官方 API 文档](https://wiki.metacubex.one/api/)。

## 构建与验收

```sh
uv sync --frozen
uv run pytest -q
uv run python scripts/sync-service-rules.py --check
./scripts/docker-build.sh amd64 5.0
./scripts/docker-export.sh amd64 5.0
```

运行验收：`/health` 正常、`/openapi.json` 显示 5.0.0、工作台加载、读取节点后完成检查/保存/重开/更新，并在客户端刷新。确认所需服务的实际登录和使用。构建自动化及隔离容器测试不会代替真实 OpenClash/Surge 导入和联网测试。
